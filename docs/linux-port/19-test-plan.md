# 19 · 测试方案

> 目标：把「感觉还有好多 bug」变成「已知的、可复现的、有主的东西」。本文件是可执行的测试计划，不是理念说明——每条用例都有编号、层级、期望与证据要求，缺陷必须能回指到用例或新增用例。

## 1. 范围

**测**：

- 移植后的全部共享功能（启动器页、游戏设置、截图、抽卡记录、战绩、设置、图库、启动链路、安装更新、账号与登录流程）；
- Lunarward 新增的「运行环境」模块（运行器发现、方案、前缀、图形层、一次性运行、诊断包）；
- 平台层：窗口/标题栏/图标、托盘（SNI + dbusmenu）、全局热键、单实例、URL 协议、截图抓取、桌面通知、剪贴板；
- CLI 全部子命令与退出码；
- 持久化：配置、方案、绑定、伴随启动、安装路径、`last-good`、原子写与损坏恢复。

**不测（当前明确不做）**：

- M4 占位功能：悬浮窗、手柄映射、RPC 服务、云游戏/战绩/BBS 的桥（入口已置灰或标「暂未实现」）；
- 纯 Wayland 原生会话下的可用性（只测「明确报错退出」这条）；
- Windows 侧构建与运行（单头 Linux）。

**测不了或代价过大的**：真实支付/真实账号风控、官方服务端行为、不同 GPU 驱动的全部组合（只在代表机型上抽样）。

## 2. 分层策略

| 层 | 名字 | 跑在哪 | 依赖 | 频率 | 判定 |
|---|---|---|---|---|---|
| L1 | 单元测试（xunit） | CI（ubuntu-latest） | 无 GUI、无 wine | 每次 push | 全绿才可合并 |
| L2 | CLI/无头集成 | CI | 临时 XDG 目录 + 假前缀/假清单，**不需要** wine 与显示 | 每次 push（冒烟子集）+ 每晚（全量） | 全绿才可合并 |
| L3 | GUI 端到端 | 本机（X11/XWayland） | 真实会话、真实 wine、cu_* 工具 | 每轮改动后手跑 + 每晚 | 关键用例必须过 |
| L4 | 人工验收 | 本机 + 真实账号/游戏 | 用户在场 | 里程碑 | 清单逐条勾选 |

### 2.5 关于 `Uno.UITest`：不采用（有证据）

- 官方文档明确列出未支持的目标：**SkiaSharp backends（GTK、WPF、Tizen）、Xamarin.macOS、Windows**；已支持只有 WebAssembly（Selenium + Chrome）与 iOS/Android（Xamarin.UITest/AppCenter）（`platform.uno` → *Using Uno.UITest* 页）。
- NuGet 上只有 4 个包且都停在 `1.0.0`：`Uno.UITest`、`Uno.UITest.Helpers`、`Uno.UITest.Xamarin`、`Uno.UITest.Selenium` —— 没有 X11/Skia 的 driver。
- 我们的目标框架是 `net10.0-desktop`（Skia + X11），所以它连「能跑」都不成立；唯一能套用的假设是把启动器编成 WASM 在浏览器里测，但 wine/GTK/X11 在那底下都不可用，测到的不是真实链路。
- 结论：**不用它**。真实输入仍靠 L3 的 `cu_*`（合成输入 + 截图 + 日志断言）。

### 2.6 可选层 L1.5：进程内 UI 断言（借鉴 Uno 的 RuntimeTests 思路）

Uno 自己那套运行时测试（`RuntimeTestPlatforms` 里有 `SkiaX11`）是在**应用进程内**跑断言：查视觉树、读 DependencyProperty、量布局，而不是注入系统输入。这个思路对我们有用，且没有 `Uno.UITest` 的平台限制：

- 形态：应用内加一个 `--selftest-ui`（`#if DEBUG` 或 `LUNARWARD_SELFTEST=1`，不进发行版副作用），启动后按用例清单逐条在 UI 线程断言，最后打印 `PASS/FAIL` 并设置退出码。
- 能覆盖：`GameBannerAndPost` 三个 tab 是否存在、切游戏后 `ItemsSource` 是否换新、图标 `Glyph` 码位、设置页根背景 Brush、InfoBar 可见性、窗口尺寸与 90% 屏幕夹取、预检对话框条目数与按钮文案。
- 不能覆盖：真实鼠标/键盘、托盘、窗口管理器行为、外部程序拉起 → 仍归 L3。
- 好处：不抢焦点、可塞进 CI（Xvfb + `xvfb-run`）、失败能精确到用例 ID。
- 代价：多一个只在测试用的应用内入口；每条断言都要在 UI 线程跑（`DispatcherQueue`），且只能断言我们自己写进代码的东西，发现不了「用户觉得丑」。

L2 的隔离方式：`XDG_CONFIG_HOME` / `XDG_DATA_HOME` / `XDG_CACHE_HOME` / `XDG_STATE_HOME` 全部指向 `mktemp -d`，由此不碰用户真实数据（三个目录均已在代码里支持）。GUI 用例也走这套环境变量，避免测试污染真实配置。

## 3. 测试矩阵

- **会话**：X11（XWayland，主力）/ 纯 Wayland（只验「exit 3 + 人话」）。
- **缩放**：DPR 1.0 / 1.25 / 1.5（窗口尺寸换算、点击坐标、截图裁切都受影响）。
- **运行器**：系统 wine（pacman/AUR）/ Steam 打包 Proton / 其它启动器（sleepy-launcher 等）/ 手动添加路径 / 不存在的路径。
- **前缀**：新建 / 复制自现有 / 使用已有 / 临时 / `~` 与相对路径 / 尾斜杠 / 只读目录 / 被占用 / 缺 `drive_c`。
- **图形层**：未选 / 已装一致 / 少一个文件 / 版本不同 / 外部前缀。
- **外部依赖缺失**：无 `libvlc`、无 `python3`+`gi`、无 `xdg-open`、无 `spectacle|grim`、无 `kdialog|zenity`、无 `fuser|lsof`（每项都要有「不崩、有提示」的用例）。
- **网络**：正常 / 超时 / 4xx / 5xx / 断流（用本地假服务器，`--sophon-probe` 与安装 CLI 都已支持自定源）。

## 5. 缺陷处理

- **入口**：GitHub Issue，模板四段：环境（`--diagnose` 附件）、复现步骤、期望 vs 实际、证据（日志行/截图/命令输出）。
- **严重度**：S1 起不来/丢数据；S2 功能不可用但有绕路；S3 观感/文案；S4 建议。S1/S2 必须先补一条可复现用例（L1/L2 优先，GUI 则 L3 脚本），再修。
- **回归规则**：每个已修 bug 在 `19-test-cases.md`（本文件 §4）里挂一个 ID；修完的提交信息必须带 ID，例如 `fix(runtime): 前缀尾斜杠 (T-LA-03)`。
- **不做的事**：不为了绿而改期望；测试里不 mock 掉被怀疑的那一层。

- L1：`dotnet test`（现有 36 条，目标覆盖 `Features/Runtime/*`、`Sophon/*`、`Helpers/*` 的纯逻辑）。
